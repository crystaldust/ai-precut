# 交付形态调研：网页版 → 跨平台桌面应用（macOS + Windows）

> 更新：2026-10-18（加入 Windows 支持评估）
> 结论先行：**桌面应用是对的；macOS + Windows 用同一套 Python + pywebview 可行，但 Windows 有一条必须先验证的硬风险——剪映 6.0+ 草稿加密。**

---

## 0. 先纠正一个前提：现在的网页版没有上传 9GB

当前架构里浏览器**只是遥控器**，既不读也不传素材：

```
浏览器 ──点击──> 本地 Python 服务(127.0.0.1) ──读文件──> 素材路径
                        └── ffmpeg 直接读磁盘，素材不出本机
```

`gui/server.py` 证据：选文件走**服务端** `osascript` 原生对话框，返回**路径字符串**；预览走 HTTP Range，要哪段读哪段；全站唯一 POST 体是分镜表 JSON（几十 KB）。

**所以"上传 9GB"不存在。你真正要解决的是"交付与安装"。**

反面也成立：如果做成远端 SaaS，9GB 就真过不去，而且还有两条更硬的约束——剪映草稿必须写进**本机**目录，ffmpeg 必须在**本机**解码。所以**形态必然是"本地应用 + 可选云端 AI"**。

---

## 1. 浏览器能不能直接读本地文件？

| 能力 | 结论 |
|---|---|
| `<input type="file">` + `createObjectURL()` | 能本地播、**不上传**，但**拿不到真实路径**，交不了给 ffmpeg / 剪映 |
| File System Access API | **只有 Chromium**：Chrome 157 ✅、Edge 154 ✅；**Safari 27 ❌、Firefox 160 ❌**（[caniuse](https://caniuse.com/native-filesystem-api)） |
| 网页里跑 ffmpeg | 不能 |

能播不能切，浏览器方案在第二步就断了。**必须有一个本地进程**，所以桌面应用是正解。

## 2. 你的三个前提（已确认）

| 项 | 结论 | 对方案的影响 |
|---|---|---|
| 个人使用、不上架 | ✅ | **不需要公证/上架审核**；Mac 用 ad-hoc 签名即可，Gatekeeper 首次右键打开 |
| 可以联网 | ✅ | **不打包 whisper**；转写继续走云端 MediaKit，安装包省下 150–500 MB |
| Apple 芯片 + Windows | ⚠️ | 见 §4，Windows 有格式风险，需要先验证 |

---

## 3. 打包路线（修正为跨平台）

| | R1 Electron + Python 后端 | R2 纯 Electron 重写后端 | R3 Tauri | **R4 PyInstaller + pywebview** |
|---|---|---|---|---|
| macOS 包体积 | ~300–350 MB | ~250–300 MB | ~120–180 MB | **~100–150 MB** |
| Windows 包体积 | ~350–400 MB | ~300 MB | ~150–200 MB | **~250–300 MB** |
| 后端改动 | 无 | **重写 ~1000 行** | 无 | **无** |
| 工具链 | Node + Python | Node | Rust + Python | **只要 Python** |
| 跨平台一致性 | 最好（自带 Chromium） | 最好 | 好 | 好（Win 用 WebView2） |
| 自动更新 | electron-updater 成熟 | 成熟 | 中 | 自己接，较麻烦 |
| 工作量 | 3–5 天 | 2–4 周 | 5–8 天 | **3–4 天（含双平台）** |

**仍然推荐 R4**，理由没变：业务代码零改动、单语言、体积小。跨平台反而是它的优势——pywebview 在 macOS 用 WKWebView、在 Windows 用 WebView2，两边都是系统自带、都能播 H.264。

代价是两个平台的系统差异要抽一层（见 §5），以及自动更新要自己做（个人使用可以先不做）。

---

## 4. Windows 支持：一条必须先验证的硬风险

### 4.1 好消息：路径和打包都不难

| 项 | Windows 情况 |
|---|---|
| 剪映草稿目录 | `C:\Users\<用户名>\AppData\Local\JianyingPro\User Data\Projects\com.lveditor.draft` |
| 沙箱 | **没有** Mac 那种 App Sandbox，素材可以留在原位置引用 |
| Python 运行时 | 同样 ~25 MB（python-build-standalone win-amd64） |
| ffmpeg | 静态 exe，ffmpeg+ffprobe 约 150–200 MB（BtbN GPL 构建） |
| 界面容器 | WebView2，Win10/11 基本随 Edge 预装；缺失时安装器带 1.5 MB bootstrapper |
| 安装包 | Inno Setup（免费）做 .exe，~250–300 MB |
| 未签名提示 | SmartScreen「Windows 已保护你的电脑」→ 点"更多信息 → 仍要运行"，个人使用可接受 |

### 4.2 坏消息：剪映 6.0+ 把草稿加密了

这是整件事的关键变量：

- 剪映**从 6.0 起**把 `draft_content.json` 存成 **AES 加密二进制**，不再是明文 JSON；
- 国际版 CapCut **不加密**，只有国内版加密；
- 5.9.x 是最后一个被广泛使用的明文版本；
- Windows 最新版已经是 **6.7 / 7.0**，也就是说客户机器上大概率是加密版。

参考：[capcut-cli 的加密决策文档](https://github.com/renezander030/capcut-cli/blob/master/docs/jianying-encryption.zh-CN.md)、[ArcReel 草稿导出指南](https://github.com/wjmboss/ArcReel/blob/main/docs/jianying-export-guide.md)。

### 4.3 但"加密"不等于"不能导入"

关键区别要说清楚：

- **加密的是存储**：剪映自己保存草稿时写密文；
- **读取明文可能是另一回事**：Mac 上我们已经实测——我们写进去的**明文** `draft_info.json`，剪映 11.0 能读、能列、能自动升级；11.6 打开后才会把它转成加密格式。

Windows 上大概率同理（同一个草稿格式家族，只是平台壳不同），而且公开的导出工具（ArcReel 等）也在给"6.0+"生成明文草稿。**但我没有 Windows 机器，没法实测——这是目前唯一没验证的环节。**

### 4.4 必须做的一次验证（1–2 小时）

在任何一台 Windows + 剪映 6.7/7.0 的机器上：

1. 把 Mac 上生成的 `九月一号_v2` 草稿目录拷过去（含 Resources）；
2. 放进 `AppData\Local\JianyingPro\User Data\Projects\com.lveditor.draft\`；
3. 启动剪映，看它是否出现在草稿列表、能否打开、时间线是否完整。

三种结果对应三种策略：

| 结果 | 策略 |
|---|---|
| **能打开** | Windows 版直接复用现有生成逻辑，只需处理路径 |
| 能列出但打不开 / 提示损坏 | 只写 `draft_content.json`（5.9 风格）再试；仍不行则降级方案 |
| 完全看不到 | **降级方案**：让客户装 5.9.x 并关闭自动更新，或只交付「分镜表 + 切片素材 + 预览片」，人工拖时间线 |

**我的建议：先做这个验证，再决定 Windows 版投入多少。** 半天的成本，能避免几天的返工。

验证包已经做好了：`windows-spike/`（含 `RUN_TEST.bat`、`spike.py`、判定标准）。拷到 Windows 上双击即可，约 10 分钟出结果。

## 5. 跨平台要抽的那一层（一次性工作，约 1 天）

现在代码里有 4 处 macOS 硬编码，必须抽成 `platform.py`：

| 现在 | 改成 |
|---|---|
| `DRAFT_ROOT = ~/Movies/JianyingPro/...` | 按平台探测：Mac 用 `~/Movies/...`，Win 用 `%LOCALAPPDATA%\JianyingPro\...`；都支持用户在设置里改 |
| `osascript -e "choose file"` | pywebview 的 `create_file_dialog`（两平台通用） |
| `open -a /Applications/VideoFusion-macOS.app` | Mac `open -a`；Win `os.startfile` |
| `platform` 字段写 `os: mac` | 按平台写；Windows 那边格式待验证 |

另外两处容易被忽略：

- **控制台编码**：Windows 终端默认 GBK，所有 `subprocess` 必须显式 `encoding="utf-8"`，日志里别用 emoji；
- **Key 存储**：Mac 用 Keychain，Windows 用 Credential Manager（`keyring` 库两边通吃），不要明文落盘。

## 6. 签名与分发（个人使用版本）

| 平台 | 需要做什么 | 成本 |
|---|---|---|
| macOS | ad-hoc 签名 `codesign -s -`，出 DMG；首次打开右键→打开 | **0** |
| Windows | 不签名，出 Inno Setup 安装包；首次运行 SmartScreen 提示 | **0** |
| 公证 / EV 证书 | **个人使用不需要**，跳过 | 省 $99/年 + $200+/年 |

> 如果以后要卖给外人，再加公证和代码签名；架构不用变。

## 7. 修订后的实施计划

**P0 · Windows 草稿验证（半天，最高优先级）**
- 在 Windows + 剪映 6.7/7.0 上跑 §4.4 的三步；
- 结论决定 Windows 版是"完整支持"还是"降级交付"。

**P1 · 跨平台抽象 + macOS 打包（2–3 天）**
- 抽 `platform.py`（路径/对话框/打开应用/Key）；
- PyInstaller `onedir` → `.app` + pywebview 窗口；
- 静态 ffmpeg 内嵌；数据目录改到 `~/Library/Application Support/`；
- 出 DMG，ad-hoc 签名。

**P2 · Windows 打包（1–2 天，依赖 P0 结论）**
- PyInstaller → `.exe`；WebView2 检测/引导安装；
- Inno Setup 安装包；SmartScreen 说明页。

**P3 · 体验打磨（按需）**
- 启动自检（ffmpeg/剪映/Key/磁盘）；
- 日志 + 一键导出诊断包；
- 自动更新（要的话再上）。

## 8. 体积预算（个人使用版，不含 whisper）

| 平台 | 组成 | 安装包 |
|---|---|---|
| macOS | Python 60 + ffmpeg 40–90 + 应用 5 | **~110–150 MB** |
| Windows | Python 60 + ffmpeg/ffprobe 150–200 + WebView2(通常已装) + 应用 5 | **~250–300 MB** |

Windows 体积大，主要是 ffmpeg 静态构建体积大；如果要压，可以只保留用到的 codec 自编译（~60 MB），但没必要。

---

## 9. 结论

1. **做桌面应用**——对，理由不是"上传"，而是"剪映在本机、ffmpeg 在本机"。
2. **R4（PyInstaller + pywebview）** 是当前最优：改动最小、双平台、体积可控。
3. **Windows 能不能成，取决于一次 1–2 小时的验证**，不是取决于代码写得多好。
4. 个人使用 + 可联网 ⇒ **不用公证、不用打包 whisper、不用自动更新**，交付成本接近 0。
